# Mediary 产品改进与实施范围

2026-09-23。依据现有 Flutter 页面、下载引擎、数据库、播放器和测试检查整理。目标是减少重复操作、提高下载成功率，并让已下载内容更容易被再次找到和观看。

## 现有能力

应用已经支持 HLS 播放列表解析、多清晰度选择、自定义请求头与 AES 密钥、并发下载、分片重试和断点续传、TS 合并与可选 MP4 remux、本地播放、历史记录、跨平台界面及中英文。核心引擎测试已通过。以下建议以这些能力为起点。

## 第一阶段：直接改善日常流程

| 功能 | 用户问题 | 验收重点 |
|---|---|---|
| 最近来源与站点模板 | 同一来源反复粘贴地址、填写请求头 | 最近链接可再次使用；模板主动保存、选择和删除；敏感请求头不在列表明文展示 |
| 自定义标题 | 自动从 URL 推导的名字常无辨识度 | 下载前可编辑标题；历史中可改名，文件仍可播放 |
| 失效链接恢复 | 含时效参数的链接重试时仍使用旧地址 | 失败任务可填写新地址、重新解析；仅相同分片结构才可复用已下载分片，否则明确从头开始 |
| 下载前预检 | 误选过大清晰度或下载到一半空间不足 | 展示码率估算体积、可用空间和不确定性；不足时警告 |
| 可管理的历史 | 内容积累后难找、已移动的文件仍像可播放 | 搜索、筛选、排序、改名、文件缺失状态 |
| 继续播放 | 每次观看都要重新寻找上次位置 | 自动保存进度；历史展示进度；可从上次位置继续 |
| 完成通知 | 长任务完成后用户不知情 | 前台及平台允许的系统通知，通知可进入播放或任务；通知权限由用户决定 |

## 第二阶段：高频用户与兼容性

| 功能 | 用户问题 | 验收重点 |
|---|---|---|
| 批量导入 | 多集逐一粘贴耗时 | 多行 URL 独立解析、预检和入队；单条失败不影响其余 |
| 队列排序与策略 | 重要任务无法优先完成 | 待处理任务可调整优先级；支持完成当前任务后再开始、仅 Wi-Fi 和充电策略；不满足条件时保留队列 |
| 现代 HLS 兼容 | fMP4 初始化段和字节范围媒体可能被错误合并 | 支持 `EXT-X-MAP`、`EXT-X-BYTERANGE` 等常见点播源；不支持的结构明确报错，不输出伪成功文件 |
| 失败诊断 | 原始异常难以理解和反馈 | 给出可读的原因、下一步操作与可复制的脱敏诊断信息 |

字幕与音轨选择不在本次实施范围。

## 本次实施结果

上述第一、二阶段项目已落地，字幕与音轨选择除外。最近来源、模板和进度均仅保存在本机；模板请求头由用户主动保存，若包含 Cookie 等敏感值，需要在应用内自行删除。下载前体积估算来自码率或分片抽样，可能与最终文件大小不同。批量导入使用同一请求头模板，失败项不会阻止其他条目入队。队列的 Wi-Fi／充电策略仅在应用进程运行且平台能够报告状态时生效，不等同于 iOS 后台常驻下载。完成通知需由用户主动开启并授权，具体展示方式取决于系统。现代 HLS 支持常见的单初始化段 fMP4 和字节范围点播；DRM、多初始化段及直播录制仍会明确拒绝。

## 优先级与风险

建议先完成重复输入、恢复与预检，再完成媒体库和播放进度，最后扩展批量、队列和 HLS 格式。链接恢复必须校验分片身份；不能因为新旧列表分片数量一样就复用旧文件。体积估算应明确为估算值。系统通知和网络/电量策略须按平台能力降级，不能承诺 iOS 后台常驻下载。模板中 Cookie 等敏感值应由用户主动保存并可删除。

## 衡量指标

可在不收集媒体 URL 或请求头的前提下，按本地或用户明确同意的匿名统计观察：再次下载的操作步数、解析成功率、失败后恢复率、完成任务的播放率、继续播放使用率、历史搜索使用率。功能上线后用这些指标和用户反馈决定后续投入。
